Networking, friends, and rooms review — September 14, 2026

Reviewed checkout: `0952c20` (Trystero 0.25.4). This is a review of the current implementation, not just the most recent commit. No production code was changed. The existing edits to `todo.md` were left intact.

The architecture can remain lightweight. Direct WebRTC media, small control messages, local identities, and shared friend connections are reasonable choices for small rooms. The main problems are trust boundaries, room lifetime management, and recovery. I would address the P1 findings before distributing builds more widely, then the P2 reliability findings. A new room database, accounts service, or media server is not needed to fix most of these.

Validation: all 76 existing tests pass; `npm run test:startup` passes, including the renderer build and isolated Electron profile checks. Twelve additional focused reproductions confirmed the behaviors described below. The reproduction script is at `C:/Users/Jeromy/AppData/Local/Temp/synced-network-review.mjs`; run it with Node from this machine. It uses extracted application functions, the actual dependency's shared peer manager, controlled doubles, and a loopback HTTP server with a synthetic subtitle. These checks demonstrate the defects; they are not passing regression tests for corrected behavior. No real media or TURN secrets were used. 1. **P1 — The documented TURN configuration ships the credential minting secret to every installer recipient.**

   Evidence: [package.json:47](<C:/Software Development/synced-video-player/package.json:47>), [main/turn.js:15](<C:/Software Development/synced-video-player/main/turn.js:15>), [.github/workflows/build.yml:35](<C:/Software Development/synced-video-player/.github/workflows/build.yml:35>), [README.md:46](<C:/Software Development/synced-video-player/README.md:46>). The workflow writes `TURN_CONFIG` into `config/turn.json`, and `extraResources` copies that file into the installed application's resources. When configured with Cloudflare, it contains the API token used to mint TURN credentials. Moving the fetch into Electron's main process does not protect an on-disk token from the person who downloaded the app. They can reuse it outside the application. Cloudflare explicitly says to keep the TURN key on the server and issue expiring credentials to apps. [Cloudflare credential documentation](https://developers.cloudflare.com/realtime/turn/generate-credentials/).

   Small fix: use a narrow credential endpoint with abuse controls, keeping the minting secret in its server environment. A small Worker is sufficient; it need not store rooms or friends. Alternatively, retain user-supplied relay configuration for private installations. If builds with a shared token have already shipped, revoke that token as part of migration. I did not inspect published installers or account credentials, so I am not claiming a live secret was exposed.

2. **P1 — A room peer can make the viewer open a peer-chosen local path or network URL through subtitle loading.**

   Evidence: [renderer/app.js:1434](<C:/Software Development/synced-video-player/renderer/app.js:1434>), [renderer/app.js:1459](<C:/Software Development/synced-video-player/renderer/app.js:1459>), [main/media.js:187](<C:/Software Development/synced-video-player/main/media.js:187>), [main/plan.js:200](<C:/Software Development/synced-video-player/main/plan.js:200>). A received host state can declare a default subtitle whose value starts with `local:`. `syncCaptionsToMedia` automatically selects it; `loadCues` treats that prefix as a local user selection and invokes `subtitleCues` with `external:<peer-controlled value>`. FFmpeg receives that value as its input. The local subtitle list is never consulted to authorize the path. A controlled test confirmed this causes a real HTTP request to a loopback server and loads its subtitle without a local file selection. This demonstrates unsolicited file/network access, not arbitrary code execution or proven file exfiltration.

   Small fix: represent local subtitles with opaque IDs mapped to locally selected paths. Only IDs present in that local map may invoke local IPC. Treat all subtitle IDs received over the room protocol as remote track IDs, regardless of their prefix; validate their schema before selecting a default.

3. **P1 — A previous room participant can make an old shared file play in a later room.**

   Evidence: [renderer/app.js:382](<C:/Software Development/synced-video-player/renderer/app.js:382>), [renderer/app.js:1176](<C:/Software Development/synced-video-player/renderer/app.js:1176>), [renderer/playlist.mjs:61](<C:/Software Development/synced-video-player/renderer/playlist.mjs:61>), [renderer/app.js:1227](<C:/Software Development/synced-video-player/renderer/app.js:1227>). `ownFiles` survives `leaveRoom`, but the playlist and removal history reset. A peer who saw an old playlist item ID can later send a `sync` snapshot claiming that item belongs to this app, then send `play`. The lookup still resolves to the old local file path. The peer does not need to know the path. This requires being connected in a later room during the same app process; it does not allow an arbitrary internet user to read arbitrary files. The focused reproduction confirmed the old path reaches `hostFile` after a room reset.

   Small fix: make the local file map part of the session and clear it on exit. Never accept a remote snapshot as authorization to create an item owned by the local peer; local ownership must match a current local selection. Test that old IDs cannot regain access after leaving and rejoining.

4. **P1 — Incoming room state can persistently break rendering and impersonate another room host.**

   Evidence: [renderer/app.js:361](<C:/Software Development/synced-video-player/renderer/app.js:361>), [renderer/app.js:666](<C:/Software Development/synced-video-player/renderer/app.js:666>), [renderer/app.js:1608](<C:/Software Development/synced-video-player/renderer/app.js:1608>). `receiveState` trusts `state.hostId`, accepts state without checking current room membership, and saves it without validating arrays, numeric fields, or nested objects. For example, a state containing `subtitles: {}` is stored, then causes `.map` to throw on every render until replaced or the room is left. A sender can also name an unrelated `hostId`, misdirecting stream selection and commands. The focused checks confirmed both. Telemetry is similarly stored without validation: a string `lossPct` between 1 and 5 reaches `.toFixed`, which throws. Command values also need validation before numeric conversion and FFmpeg restarts.

   Small fix: add small pure validators for state, commands, telemetry, subtitle results, and IDs. Validate before mutating session state. Require the transport sender to be an active peer and require a host announcement's `hostId` to match that sender. Validate audio choices against the current media and require finite seek values. A schema library is optional, not necessary.

5. **P2 — Old room callbacks continue operating on the next room's session.**

   Evidence: [renderer/app.js:299](<C:/Software Development/synced-video-player/renderer/app.js:299>), [renderer/app.js:306](<C:/Software Development/synced-video-player/renderer/app.js:306>), [renderer/app.js:361](<C:/Software Development/synced-video-player/renderer/app.js:361>), [renderer/app.js:382](<C:/Software Development/synced-video-player/renderer/app.js:382>). Peer join/leave/stream callbacks check `session.room === room`, but action callbacks mostly do not. `leaveRoom` resets the session and presents Home before awaiting Trystero's asynchronous leave. Already queued messages can therefore modify the blank or next session; even a peer-membership check is insufficient when the same peer is in both rooms. An old subtitle request handler also looks up whichever media is currently hosted. The focused test invoked an old action callback after opening a new session and confirmed it changed the new session's host.

   Small fix: bind every action/request/progress handler to its creating session and reject it when that session is no longer current. Use the same generation check after awaited host operations. Serialize enter/leave transitions; expose Home controls once cleanup is complete, or explicitly guard entry while leaving.

6. **P2 — Leaving and rejoining can silently reuse or replay a dead room.**

   Evidence: [renderer/friends.mjs:61](<C:/Software Development/synced-video-player/renderer/friends.mjs:61>), [renderer/friends.mjs:267](<C:/Software Development/synced-video-player/renderer/friends.mjs:267>), [renderer/app.js:278](<C:/Software Development/synced-video-player/renderer/app.js:278>), plus installed Trystero `core/dist/room.mjs:74`, `strategy.mjs:80`, and `shared-peer.mjs:262,329`. There are two related failures. First, `FriendNetwork.leave` discards the leave promise, and `restart` immediately rejoins desired rooms. Trystero returns the existing room until its leave completes approximately 99 ms later. Changing a username while outgoing friend requests remain queued can therefore reuse a recipient inbox that subsequently closes; the new link remains registered as if alive. A caching transport with Trystero's leave timing reproduced this. Second, Trystero buffers frames for detached rooms and replays them on rejoin. A late leave frame can eject the returning peer before application `onPeerJoin`. The actual dependency's shared peer manager reproduced buffering/replaying that leave frame. Persistent friend connections make this especially relevant because they keep the underlying transport alive.

   Small fix: await room disposal and serialize reuse per room ID. Resolve the dependency replay behavior with a narrowly scoped patch or a verified upstream fix, including a test that retains the friend connection while both users leave/rejoin the same playback room. Merely adding an arbitrary sleep does not clear frames retained on a live shared connection. The source already documents the dependency quirk in `CLAUDE.md`; it remains unresolved here.

7. **P2 — Viewers accept losing host claims after accepting a winner.**

   Evidence: [renderer/app.js:666](<C:/Software Development/synced-video-player/renderer/app.js:666>). Claims are compared only while the recipient is itself hosting. A viewer adopts every received state. With three participants, delayed state from a losing host can replace a newer winner, producing a temporary switch to the wrong stream, reset captions, and commands sent to a host that has stepped down. The focused test accepted claim 200, delivered claim 100, and confirmed the viewer switched backward.

   Small fix: maintain the accepted host claim for all roles and reject older claims independently of whether this app is hosting. Include a sequence within the claim if more than one outstanding state transmission can complete out of order. Clear or explicitly retire authority when its owner leaves. This adds a few fields, not a leader election service.

8. **P2 — Wall-clock ordering breaks normal interactions when clocks differ.**

   Evidence: [renderer/app.js:413](<C:/Software Development/synced-video-player/renderer/app.js:413>), [renderer/lib.mjs:35](<C:/Software Development/synced-video-player/renderer/lib.mjs:35>), [renderer/app.js:1202](<C:/Software Development/synced-video-player/renderer/app.js:1202>), [renderer/playlist.mjs:16](<C:/Software Development/synced-video-player/renderer/playlist.mjs:16>), [renderer/whiteboard.mjs:23](<C:/Software Development/synced-video-player/renderer/whiteboard.mjs:23>). A user whose clock is behind the host cannot take over until their timestamp exceeds the old claim. Playlist moves from the slower clock lose against previous moves. After a board clear stamped by the faster clock, new strokes from the slower clock are rejected. The host comparison and rejected new stroke were reproduced with ordinary clock skew, without malformed input.

   Small fix: use a logical revision counter advanced from observed revisions, with a peer ID tie breaker for concurrent changes. Give board clears an explicit generation so new strokes refer to the current generation rather than local wall time. Timestamps can still be used for display.

9. **P2 — Failed media opens leave viewers waiting without an authoritative end/error state.**

   Evidence: [renderer/app.js:411](<C:/Software Development/synced-video-player/renderer/app.js:411>), [renderer/app.js:431](<C:/Software Development/synced-video-player/renderer/app.js:431>), [renderer/app.js:646](<C:/Software Development/synced-video-player/renderer/app.js:646>). Hosting broadcasts a claim/loading state before opening the file. On a failed probe or image read, `stopHosting` switches the local role to idle, and the following `broadcastState` does nothing because only hosts can broadcast. The viewer remains attached to the previous loading/playing state while the peer connection stays healthy; there is no expiration for that state. Separately, player pipeline errors currently only produce a toast on the host.

   Small fix: send a terminal media state tied to the current claim before relinquishing hosting, and show a useful viewer message with the controls reset. Add a freshness check for a host whose state messages stop arriving. A missing heartbeat should report a stalled host, not silently elect somebody else.

10. **P2 — TURN setup has no bounded wait or credential renewal.**

    Evidence: [main/turn.js:18](<C:/Software Development/synced-video-player/main/turn.js:18>), [renderer/app.js:273](<C:/Software Development/synced-video-player/renderer/app.js:273>), [renderer/app.js:848](<C:/Software Development/synced-video-player/renderer/app.js:848>), [renderer/app.js:852](<C:/Software Development/synced-video-player/renderer/app.js:852>). Room creation/joining waits for credential fetching, which has no abort deadline; a stalled response can leave both Home buttons disabled. The separate friends initialization also waits for that promise indefinitely. The startup test intentionally proves Welcome/Home remain available, but not that rooms or friend controls recover from a permanently stalled request. Credentials request a 24-hour lifetime, while the friends configuration is loaded once per app process and never refreshed. Trystero's shared offer pool also captures its initial configuration, so obtaining fresh configuration for one later room does not by itself refresh all future offers. New connections after expiry can fail on networks requiring TURN. [Cloudflare documents expiring credentials and refreshing WebRTC configuration](https://developers.cloudflare.com/realtime/turn/generate-credentials/).

    Small fix: centralize credentials with a deadline, validation, expiry tracking, a cached valid result, and a visible retry state. Renew before expiry, including the configuration used to create/recycle peer connections. Test a stalled response, an error response, and credential expiry. Avoid silently treating an invalid configured relay as an intentionally STUN-only setup.

11. **P2 — Whiteboard snapshots do not converge visually, especially with the eraser.**

    Evidence: [renderer/whiteboard.mjs:27](<C:/Software Development/synced-video-player/renderer/whiteboard.mjs:27>), [renderer/whiteboard.mjs:44](<C:/Software Development/synced-video-player/renderer/whiteboard.mjs:44>), [renderer/app.js:1095](<C:/Software Development/synced-video-player/renderer/app.js:1095>). 12. **P2 — Existing limits do not bound total network memory or pending work.**

    Evidence: [renderer/app.js:472](<C:/Software Development/synced-video-player/renderer/app.js:472>), [renderer/whiteboard.mjs:13](<C:/Software Development/synced-video-player/renderer/whiteboard.mjs:13>), [renderer/playlist.mjs:53](<C:/Software Development/synced-video-player/renderer/playlist.mjs:53>), [renderer/friends.mjs:212](<C:/Software Development/synced-video-player/renderer/friends.mjs:212>), [renderer/friends.mjs:239](<C:/Software Development/synced-video-player/renderer/friends.mjs:239>), installed Trystero `core/dist/action-wire.mjs:156`, `shared-peer.mjs:329`. 13. **P2 — Room state publishes absolute local subtitle paths.**

    Evidence: [main/plan.js:76](<C:/Software Development/synced-video-player/main/plan.js:76>), [renderer/player.mjs:92](<C:/Software Development/synced-video-player/renderer/player.mjs:92>), [renderer/app.js:577](<C:/Software Development/synced-video-player/renderer/app.js:577>). 14. **P2 — A superseded image transfer can hide the current picture indefinitely.**

    Evidence: [renderer/app.js:461](<C:/Software Development/synced-video-player/renderer/app.js:461>), [renderer/app.js:472](<C:/Software Development/synced-video-player/renderer/app.js:472>), [renderer/app.js:487](<C:/Software Development/synced-video-player/renderer/app.js:487>). Sending another picture does not cancel an in-progress transfer. Actions can send chunks concurrently while waiting for data-channel backpressure, so a newer small image can finish before an older large one. `receiveImage` unconditionally revokes the previous image and retains only the last completed image per sender. When the older transfer completes last, it replaces the newer image; `shownImage` then rejects it because its ID no longer matches the current state. The viewer returns to “Receiving the picture” even though the desired image already arrived. A controlled completion-order test reproduced this result.

    Small fix: cancel superseded sends and identify images by media claim/generation. On receipt, retain the current claimed image and reject older generations; handle an image arriving before its state with a small bounded pending cache. Test large-then-small image switches under backpressure and both possible state/image arrival orders.

15. **P3 — Friend request and invitation feedback can stay misleading.**

    Evidence: [renderer/friends.mjs:85](<C:/Software Development/synced-video-player/renderer/friends.mjs:85>), [renderer/friends.mjs:113](<C:/Software Development/synced-video-player/renderer/friends.mjs:113>), [renderer/friends.mjs:157](<C:/Software Development/synced-video-player/renderer/friends.mjs:157>), [renderer/friends.mjs:170](<C:/Software Development/synced-video-player/renderer/friends.mjs:170>). Declining a friend request only deletes it locally, while the sender retains `requested: true`, stops contacting the inbox, and displays “awaiting acceptance” indefinitely. Join asks and offers similarly set their sent state before sending and swallow errors, then expire silently after two minutes. Users cannot distinguish delivery failure, no answer, or deliberate rejection. Keeping rejection private may be a product choice, but the current wording promises more certainty than the protocol provides.

    Small fix: distinguish queued/sending/delivered/expired states, show failure or timeout feedback, and provide a retry/resend action. Use a request ID for ask/answer correlation so a late reply to an old ask cannot answer a newer one. If rejection remains private, use neutral expired/unanswered wording and a bounded resend policy.

Other product and efficiency considerations:

- **Synchronization is approximate.** The host watches its local playback while viewers watch the WebRTC stream. The viewer buffer target grows from 250 ms to 1.5 s, and the host does not delay itself to match. Caption compensation changes caption timing, not media synchronization; the displayed viewer clock is extrapolated from state arrival and is not a shared presentation clock. These target values are not measurements of actual end-to-end latency. Decide whether the intended experience prioritizes smooth playback or tighter timing, measure the actual skew on two machines, and make any quality setting reflect that tradeoff. Frame-perfect synchronization or large offline buffers would require a media-path change beyond the small protocol fixes above.
- **Multiple participants are supported more broadly than telemetry is.** `sampleConnection` takes the host's sender stats from the first peer, while incoming telemetry overwrites the badge receiver with whichever viewer reported most recently. In a room with several viewers, the badge can combine different people's measurements, and one sender limitation is relayed as if universal. Keep statistics per peer and derive an explicit aggregate for the badge. For two participants the current summary is simpler and largely sufficient.
- **Room membership is possession of the room code.** Friend identity verification does not currently carry into room profiles: their `username` is accepted as text after normalization. A copied room code admits its holder, and the room calls them “Friend connected.” If this is intentional, make the distinction clear in the UI; otherwise use the existing identity machinery to verify room profiles and provide admission controls. There is no need to introduce accounts for verified identities.
- **Keep the small-room scope explicit.** Each additional viewer consumes another host media sender and upload stream. This is reasonable for small groups, but room invites have no practical participant cap or upload warning. Measure an intended maximum and communicate it. An SFU would be a separate scaling decision, not a prerequisite for this app.
- **Avoid unnecessary whole-interface work.** `render` runs four times a second and rebuilds `hostState`; host state also includes full track catalogs and viewer reports on each broadcast. This is small for typical media, so it is lower priority than correctness. If profiling shows avoidable work, separate catalog updates from changing playback fields and update friend storage only when persistent fields change. Do not add a complex delta protocol without measurements.

What is already worth preserving: signed friend hellos bound to the room and both peer IDs; checking link identity after asynchronous verification; not automatically accepting unsolicited room offers; cleaned display names and DOM text insertion; subtitle HTML escaping; persisted pending friend requests; clear distinction between creating a local room and establishing a peer connection; source-frame forwarding; backpressure on the local FFmpeg pipeline; reaction rate limiting; and pure modules with tests. These choices provide a useful foundation.

Recommended implementation order: close the subtitle/file capability and TURN secret issues; introduce session-bound handlers and schema validation; correct authority ordering and room reuse; add bounded relay recovery and explicit terminal media states; then handle board convergence, memory budgets, and friend feedback. Each step can be small and independently reviewable. Extracting the room state machine from `app.js` into a small pure module would make the missing tests possible without a framework rewrite.

Additional verification still needed before claiming network robustness: two real app instances over LAN and forced TURN; both peers leaving and rejoining while their friend connection persists; sleep/wake and Wi-Fi changes; restricted NAT and relay outages; slow image transfers while controls are used; a host failure during loading; clock skew; and three participants with asymmetric connections. The existing in-memory friend transport does not model shared WebRTC connections, deferred disposal, or dependency frame replay, so its passing tests cannot establish those behaviors. Published package contents and actual relay renewal also need validation once a safe relay configuration is available.
